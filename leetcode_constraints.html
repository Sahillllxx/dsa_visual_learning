Why Constraints Matter

▼

Constraints in LeetCode problems tell you the size of the input. This directly determines which algorithms will pass within the time limit (usually ~1-2 seconds).

💡 Key Insight: A modern computer performs roughly 108 operations per second. If your algorithm's time complexity exceeds this for the given input size, it will TLE (Time Limit Exceeded).

By reading constraints, you can reverse-engineer the expected time complexity and choose the right approach before writing a single line of code.

The Constraint → Complexity Mapping

▼

Here's the golden rule table every competitive programmer memorizes:

Constraint (n)Expected ComplexityTypical Approach
n ≤ 10O(n!) or O(2n)Brute force, permutations, backtracking
n ≤ 20O(2n)Bitmask DP, backtracking with pruning
n ≤ 100O(n3)Floyd-Warshall, cubic DP
n ≤ 1,000O(n2)Nested loops, 2D DP
n ≤ 10,000O(n2)Nested loops (tight), 2D DP
n ≤ 100,000O(n log n)Sorting, binary search, segment trees
n ≤ 1,000,000O(n) or O(n log n)Linear scan, two pointers, sliding window
n ≤ 10,000,000O(n)Linear algorithms, math
n ≤ 109O(log n) or O(√n)Binary search, math, number theory
n ≤ 1018O(log n)Binary exponentiation, math formulas
3

n ≤ 10-15 → Brute Force / Exponential

▼

When you see very small constraints like n ≤ 10 or n ≤ 15, the problem is hinting at exponential solutions.

🎯 Techniques:
  • Generate all permutations: O(n!)
  • Generate all subsets: O(2n)
  • Backtracking with/without pruning
  • Bitmask DP (when n ≤ 20)

Examples: Traveling Salesman (n ≤ 20), N-Queens, Sudoku Solver

⚠️ Note: 15! = 1,307,674,368,000 — too slow! But with memoization (bitmask DP), 220 × 20 ≈ 20 million — that's fine!

▼

This is the most common range for O(n²) DP and nested-loop solutions.

6

n ≤ 105 - 106 → O(n log n) or O(n)

▼

This is the most common constraint range on LeetCode. You need efficient algorithms.

nn log n operationsVerdict
100,000~1,700,000✔ Fast
500,000~9,500,000✔ OK
1,000,000~20,000,000✔ OK
🎯 Techniques:
  • Sorting + Binary Search
  • Two Pointers / Sliding Window
  • HashMap / HashSet (O(n))
  • Merge Sort, Quick Sort
  • Segment Tree, BIT (Fenwick Tree)
  • Monotonic Stack / Queue
  • BFS/DFS on graphs
7

n ≤ 109 → O(log n) or O(√n)

▼

When n is in the billions, you can't even iterate through all elements. You need logarithmic or mathematical solutions.

🎯 Techniques:
  • Binary Search on answer
  • Mathematical formulas (GCD, modular arithmetic)
  • Fast exponentiation
  • Sieve of Eratosthenes (up to ~107)
  • Square root decomposition
⚠️ Common Pitfall: When n ≤ 109, always check if the answer should be returned modulo 109 + 7. This hints at DP with matrix exponentiation.

Space Complexity Constraints

▼

Memory limits are typically 256MB. Here's what fits:

DataSize per elementMax elements in 256MB
int[]4 bytes~64 million
long[]8 bytes~32 million
int[][] (1000×1000)4 bytes each~4 MB ✔
int[][] (10000×10000)4 bytes each~400 MB ✘
💡 Tip: If you need a 2D DP table but n is large, consider space optimization — often you only need the previous row, reducing O(n²) space to O(n).

Integer Overflow Awareness

▼

Constraints also tell you when to worry about overflow:

TypeRangeUse When
int-2×109 to 2×109n ≤ 109 and no multiplication
long-9×1018 to 9×1018n ≤ 109 with multiplication, or sums of large values
⚠️ Red Flags for Overflow:
  • n ≤ 105 and nums[i] ≤ 105 → sum can be 1010 → use long
  • Multiplying two ints that are each ~109 → result > 1018 → use long
  • Problems asking for "modulo 109+7" → intermediate values overflow

Quick Decision Flowchart

▼

📋 Read constraint n

├── n ≤ 15 → Try all subsets/permutations

├── n ≤ 20 → Bitmask DP

├── n ≤ 100 → O(n³) is fine

├── n ≤ 1000 → O(n²) DP

├── n ≤ 105 → O(n log n) sorting/searching

├── n ≤ 106 → O(n) linear scan

├── n ≤ 109 → O(log n) binary search / math

└── n ≤ 1018 → O(log n) fast power / formula

🏆 Pro Tip: Always multiply the complexity by the constant factor. For example, O(n log n) with n = 106 gives ~20 million — safe. But O(n log²n) gives ~400 million — might be tight!
