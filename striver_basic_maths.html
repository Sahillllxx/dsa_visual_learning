Problem 01 Basic Maths → Count Digits

Count the Digits in a Number

Given an integer N, find how many digits it has. Sounds too easy? Wait till you see the 3 approaches Striver covers — and which one shines in interviews.

Bhai, ye ek warmup problem hai but it teaches you something fundamental — working with individual digits using the modulo + division trick. Every number problem in maths ultimately boils down to this. Isko acche se samjho.

Approach 1 — String Conversion (Avoid in Interviews!)

Convert N to string, return its length. Works, but it's a cheap trick. Never do this in an interview unless asked for a one-liner.

Using String.valueOf(n).length() is O(log N) internally anyway — just wasteful. Interviewers will ask you for the proper approach.

Approach 2 — Division Loop (Standard)

Keep dividing by 10 until number becomes 0. Count each division. This is the correct approach.

Core Idea digits(1234) = digits(123) + 1 = digits(12) + 2 = ... = 4
Number of times you can divide N by 10 before reaching 0 = digit count

Approach 3 — Log Formula (O(1) but tricky)

Mathematical Formula digits(N) = ⌊log₁₀(N)⌋ + 1
Fails for N=0. Also floating point precision issues for numbers like 10, 100, 1000 in some languages. Division loop is safer in practice.
Java TC: O(log N)  |  SC: O(1) 
public class CountDigits {

    // Approach 2 — Division Loop (Recommended)
    public static int countDigits(int n) {
        if (n == 0) return 1;        // edge case
        n = Math.abs(n);              // handle negatives
        int count = 0;
        while (n > 0) {
            n /= 10;               // strip last digit
            count++;
        }
        return count;
    }

    // Approach 3 — Log Formula (O(1) but risky)
    public static int countDigitsLog(int n) {
        if (n == 0) return 1;
        return (int) Math.floor(Math.log10(Math.abs(n))) + 1;
    }

    public static void main(String[] args) {
        System.out.println(countDigits(12345));  // 5
        System.out.println(countDigits(7));      // 1
        System.out.println(countDigits(0));      // 1
    }
}

Interview follow-up: "Count digits of N that evenly divide N." Just extract each digit via % 10, check if digit != 0 && N % digit == 0, count such digits.
Problem 02 Basic Maths → Reverse a Number

Reverse a Number

Given N = 1234, return 4321. Classic digit manipulation. This is the foundation for palindrome checking.

Yaar, reverse number ka pattern ek hi hai — extract last digit via % 10, build reversed number by multiplying by 10, strip last digit via / 10. Isko ek baar samjho, palindrome, Armstrong — sab ban jaayega.

The Core Pattern — Extract → Build → Strip

The Loop Invariant last_digit = N % 10
reversed = reversed * 10 + last_digit
N = N / 10      ← strip last digit

public class ReverseNumber {

    public static int reverse(int n) {
        int rev = 0;
        while (n != 0) {
            int digit = n % 10;    // extract last digit
            rev = rev * 10 + digit; // build reversed
            n /= 10;               // strip last digit
        }
        return rev;
    }

    public static void main(String[] args) {
        System.out.println(reverse(1234));    // 4321
        System.out.println(reverse(-120));   // -21 (trailing zeros dropped)
        System.out.println(reverse(1534236)); // 6324351
    }
}
For LC 7 (Reverse Integer), check for integer overflow BEFORE multiplying: if (rev > Integer.MAX_VALUE/10) return 0.
This exact pattern — extract last digit with % 10 — is the skeleton of 90% of all basic maths problems. Internalize it.
Problem 03 Basic Maths → Palindrome Number

Check Palindrome Number

A number is a palindrome if it equals its reverse. 121 → palindrome. 1231 → not a palindrome. LC 9.

Ek baar reverse karna aaya, to palindrome ekdum easy hai bhai. Reverse the number, compare. Done. But there's also a half-reversal trick that's more optimal. I'll show you both.

Approach 1 — Full Reversal (Simple)

Reverse the number using the same pattern from Problem 2. If rev == original, it's a palindrome.

Negative numbers are never palindromes (because of the minus sign). Return false immediately for n < 0.

Approach 2 — Half Reversal (Optimal, used in LC 9)

Reverse only half the number. Compare with the other half. Avoids potential overflow from reversing large numbers.

public class PalindromeNumber {

    // Approach 1 — Full reversal
    public static boolean isPalindrome(int n) {
        if (n < 0) return false;    // negatives never palindrome
        int original = n, rev = 0;
        while (n != 0) {
            rev = rev * 10 + n % 10;
            n /= 10;
        }
        return original == rev;
    }

    // Approach 2 — Half reversal (LC 9 optimal)
    public static boolean isPalindromeOpt(int n) {
        if (n < 0 || (n % 10 == 0 && n != 0)) return false;
        int rev = 0;
        while (n > rev) {            // stop at midpoint
            rev = rev * 10 + n % 10;
            n /= 10;
        }
        // odd digits: n == rev/10 (ignore middle digit)
        return n == rev || n == rev / 10;
    }
}
Numbers ending in 0 (except 0 itself) cannot be palindromes — because no number starts with 0. This is the extra check in Approach 2.
Problem 04 Basic Maths → GCD / HCF

GCD & HCF — Euclidean Algorithm

Find the Greatest Common Divisor of two numbers. This is one of the most important algorithms you'll ever learn. It's used inside LCM, fraction simplification, cryptography, and Competitive Programming constantly.

GCD ka Euclidean algorithm is a masterpiece of efficiency. Brute force is O(min(a,b)). Euclidean makes it O(log(min(a,b))). The beautiful insight: GCD(a, b) = GCD(b, a%b). That's it. That's the whole algorithm.

Why Does GCD(a,b) = GCD(b, a%b)?

If d divides both a and b, it must also divide a-b, a-2b, … a%b. So any common divisor of (a,b) is also a common divisor of (b, a%b). Hence the GCDs are the same!

Euclidean Algorithm GCD(a, 0) = a                ← base case
GCD(a, b) = GCD(b, a % b)   ← recursive step

public class GCD {

    // Recursive Euclidean
    public static int gcd(int a, int b) {
        if (b == 0) return a;
        return gcd(b, a % b);
    }

    // Iterative Euclidean (preferred — no stack overhead)
    public static int gcdIter(int a, int b) {
        while (b != 0) {
            int temp = b;
            b = a % b;
            a = temp;
        }
        return a;
    }

    // LCM using GCD: lcm(a,b) = (a/gcd) * b  ← avoids overflow
    public static long lcm(int a, int b) {
        return (long) a / gcdIter(a, b) * b;
    }
}
Brute Force
O(min(a,b))
Check every number from 1 to min
Euclidean
O(log min)
Fibonacci worst case — insanely fast
LCM(a,b) = (a × b) / GCD(a,b). But compute it as (a / gcd) × b to avoid integer overflow — divide first, then multiply!
Problem 05 Basic Maths → Armstrong Numbers

Armstrong Numbers

A number is Armstrong if the sum of each digit raised to the power of the number of digits equals the number itself. 153 = 1³ + 5³ + 3³ = 1 + 125 + 27 = 153 ✅

Armstrong number ka concept simple hai — digit count karo, phir har digit ko us power pe raise karo, sum karo, compare karo. This is a direct application of the digit extraction pattern we already know. Notice the count digits + reverse loop combined.

Armstrong Number Condition Let k = number of digits in N
N is Armstrong if: N = d₁ᵏ + d₂ᵏ + d₃ᵏ + ... (for each digit dᵢ)

public class Armstrong {

    public static boolean isArmstrong(int n) {
        int original = n;
        int k = String.valueOf(n).length(); // number of digits
        // Or use the division loop to count digits
        int sum = 0;
        while (n > 0) {
            int digit = n % 10;
            sum += (int) Math.pow(digit, k); // digitᵏ
            n /= 10;
        }
        return sum == original;
    }

    public static void main(String[] args) {
        System.out.println(isArmstrong(153));  // true
        System.out.println(isArmstrong(123));  // false
        System.out.println(isArmstrong(1634)); // true
    }
}
You can also write a helper power(base, exp) using a loop instead of Math.pow to avoid floating-point issues for very large numbers.
Problem 06 Basic Maths → Print All Divisors

Print All Divisors

Find all numbers that divide N completely (remainder = 0). This problem has a beautiful sqrt(N) optimization that you must know cold.

Brute force — loop from 1 to N, check if i divides N — is O(N). But notice: divisors always come in pairs! If i divides N, then N/i also divides N. So we only need to loop till √N. That takes it from O(N) to O(√N). Massive win!

The √N Insight — Visualized

For N = 36: pairs are (1,36), (2,18), (3,12), (4,9), (6,6). Both elements of each pair are divisors. Loop only till √36 = 6, get both in one iteration!
Key Optimization If i divides N → both i and N/i are divisors
Loop from i = 1 to √N → add both i and N/i
Special case: if i == N/i (perfect square), add only once

import java.util.*;

public class Divisors {

    // Brute Force — O(N)
    public static List<Integer> bruteDivisors(int n) {
        List<Integer> divs = new ArrayList<>();
        for (int i = 1; i <= n; i++) {
            if (n % i == 0) divs.add(i);
        }
        return divs;
    }

    // Optimal — O(√N)  ← Always use this!
    public static List<Integer> getDivisors(int n) {
        List<Integer> divs = new ArrayList<>();
        for (int i = 1; (long) i * i <= n; i++) {
            if (n % i == 0) {
                divs.add(i);
                if (i != n / i) divs.add(n / i); // avoid duplicate if perfect square
            }
        }
        Collections.sort(divs);  // optional: sort them
        return divs;
    }
}
Sum of divisors, count of divisors, check if N is perfect number (sum of proper divisors = N) — all use this same O(√N) loop. Master this pattern.
Problem 07 Basic Maths → Check Prime

Check if a Number is Prime

A prime number has exactly 2 divisors: 1 and itself. The √N trick from divisors applies here directly. Then there's the "6k±1" optimization for extra speed.

Prime checking is directly connected to the divisors problem. A prime has exactly 2 divisors. Check divisors till √N — if you find any divisor other than 1, it's not prime. That's O(√N). But there's an even smarter check using 6k±1 that I want to show you.

Why Loop Till √N?

If N is not prime, it has a factor ≤ √N. Proof: if both factors were > √N, their product would be > N. Contradiction. So we only need to check till √N.

6k ± 1 Optimization All primes > 3 are of the form 6k-1 or 6k+1
(Because 6k, 6k+2, 6k+4 are even; 6k+3 is divisible by 3)
So skip all i that aren't 6k±1 → ~3× faster

public class Prime {

    // Standard O(√N)
    public static boolean isPrime(int n) {
        if (n <= 1) return false;
        if (n <= 3) return true;
        if (n % 2 == 0 || n % 3 == 0) return false;
        for (int i = 5; (long) i * i <= n; i += 2) {
            if (n % i == 0) return false;
        }
        return true;
    }

    // Optimized with 6k±1 trick
    public static boolean isPrimeOpt(int n) {
        if (n <= 1) return false;
        if (n <= 3) return true;
        if (n % 2 == 0 || n % 3 == 0) return false;
        for (int i = 5; (long) i * i <= n; i += 6) {
            // check 6k-1 and 6k+1
            if (n % i == 0 || n % (i + 2) == 0) return false;
        }
        return true;
    }

    // Sieve of Eratosthenes — find ALL primes till N in O(N log log N)
    public static boolean[] sieve(int n) {
        boolean[] isPrime = new boolean[n + 1];
        Arrays.fill(isPrime, true);
        isPrime[0] = isPrime[1] = false;
        for (int i = 2; (long) i * i <= n; i++) {
            if (isPrime[i]) {
                for (int j = i * i; j <= n; j += i)
                    isPrime[j] = false;
            }
        }
        return isPrime;
    }
}
The Sieve of Eratosthenes is the go-to for "count primes up to N" or "find all primes in range". Time: O(N log log N). It's practically linear for most inputs.
When N can be up to 10⁶ or 10⁷, always use Sieve. For a single query on large N, use the 6k±1 check. Know when to use which!

Q1. What is the time complexity of counting digits in N using the division loop?
A) O(N)
B) O(log₁₀ N)
C) O(√N)
D) O(1)
Each division by 10 reduces N by a factor of 10. So the loop runs ⌊log₁₀N⌋ + 1 times = O(log N).
Q2. For GCD(48, 18) using Euclidean algorithm, what are the steps?
A) GCD(48,18) → GCD(18,30) → GCD(30,18) → 18
B) GCD(48,18) → GCD(18,12) → GCD(12,6) → GCD(6,0) → 6
C) GCD(48,18) → GCD(30,18) → GCD(12,6) → 6
D) GCD(48,18) → GCD(18,6) → GCD(6,0) → 6
48%18=12 → GCD(18,12). 18%12=6 → GCD(12,6). 12%6=0 → GCD(6,0) = 6. Always a%b, not a-b.
Q3. Why do we loop till √N when finding all divisors?
A) Because divisors above √N are always prime
B) Divisors come in pairs (i, N/i) — if one is ≤ √N, the other is ≥ √N
C) Numbers above √N don't divide N
D) It's just a convention in textbooks
Every divisor i ≤ √N has a partner N/i ≥ √N. So looping till √N and collecting both covers all divisors in O(√N) instead of O(N).
Q4. Is 370 an Armstrong number? (3-digit number)
A) Yes — 3³ + 7³ + 0³ = 27 + 343 + 0 = 370
B) No — 3+7+0 = 10 ≠ 370
C) Yes — 3² + 7² + 0² = 58 ≠ 370
D) Not enough info
k=3 digits. 3³=27, 7³=343, 0³=0. Sum = 370. Yes, Armstrong! Always raise to the power of digit count, not 2 or 3.
Q5. What makes the 6k±1 trick useful for prime checking?
A) It checks all numbers divisible by 6
B) It eliminates the need to check √N
C) All primes >3 are 6k±1, so we skip ~66% of numbers
D) It only works for numbers < 100
Of 6 consecutive numbers, 4 are eliminated: multiples of 2 (6k,6k+2,6k+4) and multiple of 3 (6k+3). Only 6k+1 and 6k+5 (=6k-1) need checking. That's ~33% of candidates vs 50% with just skipping evens.
Q6. To reverse integer N and avoid overflow in Java (LC 7), you should:
A) Use long for reversed and cast at end
B) Check rev > Integer.MAX_VALUE/10 BEFORE multiplying by 10
C) Use try-catch for ArithmeticException
D) Only reverse if N < 10000
Check if (rev > Integer.MAX_VALUE / 10) before doing rev * 10 + digit. If rev is already larger than MAX_VALUE/10, multiplying by 10 would overflow. Return 0 in that case.
